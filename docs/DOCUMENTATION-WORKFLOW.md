# 文档同步工作流

适用范围：仅 WristFlow 仓库。同步是变更完成条件，由主代理负责；不改用户级 Codex 配置，不强制每次派子代理。

## 检查点与分工

1. **开始/接续任务**：先核对工作树、分支、HEAD 和未提交改动，再读 STATUS、BASELINE、BUILD。不同工作树的文档只代表各自版本；隔离工作树中的最新结果不能由旧目录的状态页替代。
2. **用户决定或验证结果变化**：及时更新对应文档。长任务按有意义的阶段记录，不等到整个任务结束；失败、阻断和未完成也要留下可续接状态。
3. **提交/PR 前**：对照差异检查下面的职责表，只更新受影响的文档；不需要修改的文件不用制造改动。文档与实现放在同一 PR，主代理审阅最终差异与关键证据。
4. **验证/真机反馈/交接后**：核对结果对应的提交或源码哈希。需要改变已提交结论时补充文档提交，并对受影响行为重新验证；手动云端基线仅在需要干净环境证据时执行。PR 合并状态可由 PR 链接实时查询，不为每次状态变动产生一轮无意义的文档提交。

短小更新以及主代理已掌握的事实由主代理直接写。需要跨目录检索、大量日志压缩或独立核验时，才使用现有 `default`/`verification` 代理；优先在已经必要的检索或验证任务中附带文档差异定位，避免再派一次代理重复读取。派发使用 `fork_turns="none"`、一轮任务；默认 Sol/low，只有满足用户通用规则中的具体复杂推理条件才用 medium。

子代理仍不写项目文档。交接只需工作树/分支/HEAD、确切证据路径或 `file:line`、需要更正的事实与未覆盖项，不要求长草稿；主代理抽查承重证据并直接修改原文，避免先生成全文再重写。分工主要减少主线程材料，不承诺总 token 一定更少。架构、设计、共识等奠基性文档由主代理完整阅读并决定改法。

## 文档职责与证据

| 发生变化 | 更新位置 | 必须保留 |
|---|---|---|
| 当前阶段、阻断、已完成项、下一步 | `docs/STATUS.md` | 当前事实、版本和一个有界的下一实验；旧进度移入带日期记录，不继续作为待办 |
| 范围、预算、路线等已确认决定 | `docs/BASELINE.md` | 用户决定的日期、适用阶段、被覆盖的旧决定；建议标为待定 |
| 硬件、接线、供电与实测条件 | `docs/HARDWARE.md` | 实际连接条件和未核实项，区分资料配置与实物验证 |
| 构建入口、工具链、可复现命令 | `docs/BUILD.md` | 版本、命令、失败处理；详细增量结果可链接到专题记录 |
| 交互或模块行为 | 对应的 `docs/UI-*.md` 等专题文档 | 最终行为、约束、验证范围；历史记录标明日期/版本 |
| 构建、测试、串口、测量 | 专题记录及必要的 `docs/evidence/` 摘录 | 源码/固件标识、命令、退出码、产物位置、失败和未覆盖项 |

原始长日志、构建目录和截图优先留在忽略的 `artifacts/`，只提交必要的精简证据；本机证据要注明所在工作树，不能把未提交的本地路径写成仓库内可用链接。`STATUS.md` 只保存摘要和索引，完整哈希、长命令和同一决定不在多页反复复制。

源码检查、成功编译和硬件验证分别记录。没有电池时不显示虚构的电池百分比，不声称电池续航；USB 下若测电流，须注明测量轨和额外板载负载。没有测量时不能由黑屏、编译配置或主观流畅度推断休眠电流和续航。

## 完成条件

- 受影响文档与实际行为、用户已确认决定、证据版本一致；历史内容明确标为历史。
- 检查改动文件的 UTF-8、相对链接、命令与 `git diff --check`，不扫描无关中文文件。
- PR 模板填写同步文件与证据，或说明为何无需文档变化。主代理负责语义一致性；修改一个任意 docs 文件不能证明已同步。
- 纯文档变更不为凑证据新增本地固件构建或硬件实验；文档同步不要求自动云端 CI。需要干净环境证据时再手动运行基线；文档检查不作为独立固件验收结论。

## CI 路径与等待时间

当前工作流只响应手动 `workflow_dispatch`。它保留一次完整的干净 Windows runner 基线，用于更换 SDK、工具链、公共构建入口或阶段验收；PR 和 push 不下载 SDK、不启动云端构建，也没有自动必需状态检查。日常验证由本地主机测试、受影响目标编译和真机实验承担。

2026-09-25 对比实际 Actions：旧 F411 项目的[纯文档运行](https://github.com/e-n-ye/magic-watch-workflow/actions/runs/33390350626)为 14 秒，[代码运行](https://github.com/e-n-ye/magic-watch-workflow/actions/runs/33629906306)为 71 秒；后者容器初始化 17 秒、F411 编译 18 秒，主机作业独立并行。WristFlow [PR #17 原完整运行](https://github.com/e-n-ye/wristflow/actions/runs/36117461804)约 11 分钟：checkout 48 秒、SDK 安装 72 秒、Hello 44 秒、BLE 58 秒、Bringup 156 秒、UI Demo 175 秒、PC 主机 100 秒，主要步骤串行。差异包含工具预装、调度方式和不同工程的编译量，不能全归因于 Windows 或安装。

完整冷构建约 11 分钟，当前阶段不值得让每个 PR 等待。手动运行期间继续在独立工作树推进工作；记录运行对应的提交、版本、产物和失败位置，不把手动基线结果扩大成真机 BLE、低功耗或续航结论。

2026-09-25 已将规则接入项目 AGENTS、CONTRIBUTING 和 PR 模板；本次修正取消日常自动 CI 与合并等待，保留手动完整基线。没有新增强制文档代理；小更新由主代理直接完成。下一次产品固件增量按此流程同步真实时间、设置恢复及其证据。
