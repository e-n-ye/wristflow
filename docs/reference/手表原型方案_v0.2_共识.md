# 手表原型方案 v0.2：共识基线

确认日期：2026-09-21。依据：本次访谈 Q1～Q60 及用户最终确认。

状态：需求、验证顺序和路线判断规则已确认；具体主板、屏幕、报价、工具和性能仍需核验。此次仅整理方案，没有采购、修改固件或进行硬件实测。本文件取代 [v0.1 历史草案](./手表原型方案_v0.1.md)。

## 1. 已决定：目标与投入

核心目标是做出低功耗、交互合理、显示观感满意的手表。Redmi Watch 4 是操作与产品体验参照。最终希望愿意连续日常佩戴；首个三个月允许结构偏厚、外观粗糙，只适合手持或短时佩戴，但 UI 与低功耗必须在同一个实体系统上成立。

- 时间：每周可投入 20～40 小时，按每周 20 小时、十二周约 240 小时排期。额外时间作为余量；以下周次相对项目启动计算，不假定硬件已到货。
- 首笔新增预算：500 元。后续可以凭阶段成果追加，但不存在预先授权的无限预算。
- 三个月成果：电池独立供电的原型、完整的核心交互路径、真实负载下的功耗记录、实测续航和下一步路线判断。
- 续航：七天为路线判断目标，十四天以上为长期争取方向。允许平时熄屏。
- 所有权标准：能解释、修改、定位故障并掌握关键取舍；允许使用成熟组件、公开 SDK 和 AI。
- 长期价值：睡眠能力必须继续完善，不能以“首版不做”为由无限后置；基础计步与睡眠阶段并行。

## 2. 已决定：首版产品范围

| 范围 | 共识 |
|---|---|
| 屏幕 | 直接验证矩形 AMOLED 触摸屏，目标分辨率接近 390×450，368×448 为可接受下限；不默认改为圆屏 |
| 主界面 | 一个认真打磨的表盘、左右卡片 |
| 全局入口 | 通知中心、快捷设置、应用列表 |
| 基础应用 | 闹钟、秒表、倒计时、真实传感器心率页面 |
| 设置 | 亮度、熄屏时间、勿扰、连接策略、唤醒方式、电量、日间与夜间心率采样配置 |
| 实体输入 | 触摸加一个实体按键；表冠后置，目标是接近 Watch 4 的操作形态，不用不满意的横向编码器代替 |
| 提醒 | 基础振动纳入首版，允许外接电机与驱动，不追求复杂触感 |
| 唤醒 | 先完成按键路径；抬腕/翻腕、遮盖熄屏作为可配置能力，核验 IMU 与触控硬件后实现 |
| 手机 | 现有 iQOO Android 手机；先短实验验证 Gadgetbridge 接入 |
| 暂缓 | 自动亮度、自动佩戴检测、精致表壳、旋转表冠、运动中心率准确度、复杂运动识别 |

核心交互须满足跟手、可反向与取消、合理吸附、列表位置保留、详情返回和连续操作不乱。验收使用实际手感与帧间隔记录，不把“示例亮屏”或平均 60fps 视为充分条件。

新功能必须说明它占用的时间与功耗，以及挤掉哪项工作。新增页面和新增后台采样、手机服务、机械接触条件分别估算。

### 2.1 亮度与亮灭屏

- 手动亮度使用滑块，用户范围为 10%～100%，设置持久化。具体 PWM/显示控制器数值和视觉亮度映射依屏幕验证。
- 自动亮度是明确的后续能力，首版不依赖环境光传感器。
- 自动熄屏前进入变暗过渡态：默认在到期前 5～10 秒降到当前亮度约 20%，不改写保存值。
- 触摸、按键或当前模式允许的有效抬腕事件恢复亮度；到期后关闭屏幕。
- 变暗亮度受屏幕实际支持下限约束；较短熄屏时长的过渡区间需缩短，不能生成负的等待时间。这些参数在真机体验中确定。
- 睡眠模式可以直接关闭屏幕，跳过变暗过渡，不覆盖日常亮度；手动唤醒、自动抬腕和闹钟行为分别测试。

### 2.2 连接、消息与佩戴

日常使用时保持 BLE 逻辑连接，以通常几秒内收到通知为目标；连接期间射频可周期休眠，不能用“保持连接”等同“持续射频工作”。

省电/收纳模式不保持实时连接。用户希望未来自动识别佩戴状态，再根据离腕、亮屏和同步需要调整连接；首版不把静止或熄屏视为离腕，不新增手动“佩戴中/离腕”标签来冒充检测。首版由明确的日常、省电和睡眠设置驱动策略。

睡眠默认不受通知打扰，并默认断开实时 BLE，早晨主动重连同步。保留夜间连接与消息提醒的配置方向。连接开关和通知勿扰是两项策略，保持连接不应自动开启振动打扰，闹钟也应有独立行为。

自动离腕断连与离线通知补送策略后置。暂不承诺补送最新几条、全部未读或任意离线消息；重连后的能力以手机协议验证结果为准。

## 3. 已决定：硬件验证方向与采购门槛

先寻找同时具备图形能力、BLE 和已适配 AMOLED 的平台，思澈 SF32LB52 系列是首个待验证候选。选择依据是容易获得真实成果、关键能力可开发和可调试，不是已经证明它优于所有平台。

不预设外置 Nordic 加 H7 的双芯片方案，也不预设每次灭屏都切断显示 MCU 电源。Nordic 与双芯片保留为证据需要时再比较的路线；引入第二颗芯片前明确收益、供电、通信与恢复成本。

主采购必须满足以下条件：

| 条件 | 采购前证据 |
|---|---|
| AMOLED 与触摸 | 明确主板版本、屏幕/触控型号、分辨率、黑边尺寸、接口电压、连接件、驱动和可运行示例 |
| SDK | 能获得所需工具链与代码，理解源码与二进制边界，有显示、输入、BLE 和低功耗调试路径 |
| PPG、IMU | 可用 I2C/SPI、供电与中断；PPG 和六轴 IMU 能控制工作状态，传感器活动不要求系统一直满速运行 |
| 时钟与保存 | RTC/稳定时间基准、非易失存储、记录与同步路径；按实际数据格式和采样量核算空间 |
| 电源与测量 | 台式电源接入点、电池阶段的充电保护路径、可分离或识别调试器和板上附加电路耗电 |
| 振动 | 允许外接，但确认驱动、电源和控制接口；不能直接假设 GPIO 能带动电机 |
| 完整价格 | 主板、AMOLED、触摸、必要连接与供电附件及运费的合计，不只看裸板价 |

没有可核验的 AMOLED 组合，就不把平台作为主采购。不新买普通 LCD 套件来替代 AMOLED 产品验证。已有 H7/F411 可以做机制实验，不能替代目标板的显示与功耗验收。

首次完整组合超过 500 元时，先提供物料、差额和用途，再讨论预算；不得自行把分阶段预算理解为可以直接超支。

## 5. 前两周验证与停止条件

两周约 40 小时是首次路线评审点。采购与到货属于三个月日历时间；等板期间完成 Watch 4 操作记录、旧代码定位、测量准备和协议阅读。硬件未到或事实未核实时，不把未做的实验记为通过。

| 验证 | 最小结果 | 不通过时的处理 |
|---|---|---|
| 开发基线 | 编译、烧录并修改官方示例；记录 SDK 和工具版本 | 列出阻断点，不能把封闭能力缺失当作普通学习进度无限延长 |
| AMOLED UI | 表盘、卡片拖动/反向/取消、列表、详情返回原位置；快速操作无明显错页、卡死、状态丢失 | 测量输入、渲染、传输和内存瓶颈；不继续堆页面 |
| 亮灭屏 | 按键唤醒、变暗、熄屏、低功耗、再次唤醒 | 检查实际电源状态和占用，不用黑屏代替休眠 |
| BLE | 广播、连接、自定义服务、断开重连、休眠下连接/事件行为 | 分清 SDK、协议、手机权限和后台问题 |
| 功耗 | 屏亮交互、屏灭未连接、屏灭已连接、一次通知及一次唤醒的实测记录 | 判断预算最大项，必要时调整平台，避免只调 BLE 参数 |
| 扩展 | PPG/IMU 电气和接口检查、RTC/存储路径、振动接入路径 | 没有明确路径时，不因 UI 示例漂亮而继续主采购或扩展投入 |

Gadgetbridge 协议试验累计最多 8 小时，记录平台前置准备与协议调试各自用时。目标是广播/连接、一条真实测试通知、通知删除、主动断开与重连，以及手机权限和后台观察。不在这一步完成所有通知 UI。

八小时内未形成最小可用路径，就取消 Gadgetbridge 的默认地位，评估最小 Android 伴侣 App 的实际成本。时间到不证明 Gadgetbridge 技术上不可行，也不自动证明自研 App 更容易；切换时必须明确失败原因和新路径成本。

首次评审结论为继续、提出下一项限时实验、换路线或停止。不得只写“再优化一下”；每项追加实验说明问题、预计时间和结束条件。

## 6. 已决定：功耗基准与续航判断

### 6.1 首轮固定负载

| 项目 | 基准与配置 |
|---|---|
| 亮屏 | 每天交互合计 45 分钟；熄屏不计入，变暗阶段单独记录并计入亮屏耗电 |
| 通知 | 每天 30 次，其中 5 次点开或滑动处理；包含首版振动行为 |
| 连接 | 日常模式保持 BLE 逻辑连接；省电/收纳不实时连接；记录每天各模式时长 |
| 心率 | 日间默认每 10 分钟尝试一次；夜间独立可配置，不限制为仅日间采样 |
| 采样边界 | 固定单次超时、最多一次重试；具体窗口由信号与功耗实验确定并记录 |
| 显示配置 | 关闭常亮显示；亮度滑块可调，但每轮实验固定并记录默认值、画面和熄屏参数 |
| 睡眠 | 手动或计划时段，记录连接、采样和勿扰配置；夜间采样也计入日耗电 |

仍待确定的测试参数包括亮度默认值、各模式时长、夜间采样间隔及采样窗口。这些由首轮实验和实际使用确定，未固定前不能声称两次续航结果具有同等负载。

### 6.2 电池比较与测量

300mAh 作为比较基准，预留 20% 容量余量，不是最终电池采购承诺：

`七天每日可用电量 = 300 × 0.8 ÷ 7 ≈ 34.3mAh`

`对应整机平均电流 ≈ 1.43mA`

每天亮屏 45 分钟时，即使其余负载为零，亮屏平均电流也须低于约 45.7mA 才能留在上述预算内。实际还要给待机、无线、传感器与振动留出空间。例如亮屏 100mA 会消耗 75mAh/天，仅此一项已超过预算。这里的电流是算例，不是候选板实测值。

初期使用台式电源调试，先分解负载，再选择实际电池、充电和保护方案。最终依据电池可用容量、尺寸、电压和转换效率修订预算，不用任意增大电池掩盖高功耗。

测量统一说明供电位置；优先从电池侧或等效输入侧积分，覆盖整机负载。测某个电源轨时注明范围，不能把 MCU 或传感器单项电流当作整机电流。识别调试器、日志、指示灯、稳压器与充电电路的额外消耗。

借用工具先核对规格并校验。磁场式探头未必适合微安休眠，普通万用表也可能漏掉脉冲；根据量程与带宽选分流测量或其他可借设备，并记录压降和测量误差。

### 6.3 七天目标的路线判断

三个月末在固定负载下实测电池运行时间。短期能量积分与容量换算标记为预计续航，不能写成实际跑满七天。

若未达七天：交付耗电分解和实测条件。有明确主要耗电项、具体改进实验和可接受成本时，可以继续；若主要限制来自平台且缺少可行改进，暂停追加投入并重评路线。不要求先“优化到极限”才能重评，也不因一个孤立的续航数字否定已经得到的证据。

## 7. 已决定：传感器、睡眠与数据边界

### 7.1 三个月内的采集与策略

先在已有 F411 上验证 MAX30102 启停、超时、失败重试和测量方法。新平台预留接口；进入首版心率验收前再合理接入或购买独立模块，不为省模块破坏现有手表。F411 整板电流不能替代最终传感器负载。

心率页面支持手动与周期采样、结果时间、有效/无效/未测量标识。首版目的在于控制真实负载，不以准确心率为主验收；没有有效数据就显示无效，不能用固定模拟数值冒充测量。

每次任务有启动、完成、取消、超时和最多一次重试，退出后释放阻止休眠的资源。测试关闭采样、正常采样、无信号、设备失联与连续触发。加入新传感器必须复测增量耗电和旧功能稳定性。

首组融合传感器为 PPG、六轴 IMU，加 RTC 时间基准。六轴器件不意味着陀螺仪必须全天开启，实际通道与采样策略随实验确定。

首版睡眠模式由手动或固定时间段启动；形成夜间时间戳、心率/信号质量、失败原因、运动事件和基本记录查看路径。暂不要求自动入睡识别或可信评分。后续完善自动识别是已确认需求。

### 7.2 数据保存与手机计算

手表负责采样、时间戳、信号质量、运动事件、低功耗调度与保存；手机承担后续睡眠统计、阶段与评分，手表显示最近结果摘要。

保存策略为摘要优先：心率结果、质量、失败原因、运动事件和时间。信号异常、明显运动或判断不确定时保留短原始片段，默认不保存整夜高采样率 PPG。容量、片段上限、写入量和同步能耗按数据格式核算。

能力边界：每十分钟一次心率、稀疏摘要和异常片段是否足以支持所选睡眠算法，尚未证明。数据不足时标记无法判断，并在后续阶段检验采样策略、正常样本覆盖和存储预算；不凭稀疏采样直接承诺睡眠分期或 HRV 能力。

Gadgetbridge 通知协议通过，不代表已经具备私有夜间数据同步、手机评分、历史存储和结果回传。手机端算法来源、许可、运行载体、输入要求及同步协议是睡眠阶段的显式待验证工作，不能隐含在“现成 App 可用”之中。

### 7.3 三个月后的首个正式阶段

时间盒为 4～6 周，睡眠完善为主验收，基础计步并行且不阻塞主线。计步先实现持续记录、日总步数、跨天和同步，准确率及复杂运动识别后续校准。

睡眠长期完成线：自动识别入睡、醒来与主要中断，睡眠时长和基础统计，心率与 IMU 支持的阶段与质量评分，历史趋势与手机同步。与 Redmi Watch 4 对照操作、信息组织和多晚趋势，不要求分数相同；Watch 4 不作为医学真值。

阶段安排：前 1～2 周核验采集、整夜功耗、手机同步及算法输入条件；第 3～4 周验证自动窗口和中断识别；第 5～6 周整合统计、第一版阶段/评分和历史展示。算法效果是验证目标，不是时间盒所能保证的结果。

阶段结束至少检查七晚真实佩戴数据、自动结果、统计与评分、同步、信号质量、功耗和 Watch 4 对照。稳定贴肤与数据质量是采样前提，首版允许外壳粗糙不免除这个要求。差异仅在已有数据支持的范围内解释，不能保证稀疏片段能解释每个差异。

六周后链路仍零散或同步不稳定，则暂停增加传感器，先修链路；链路稳定而评分不理想，进入明确的算法评估和迭代。不能从趋势接近直接推断分期准确。

自动佩戴检测不是自动睡眠的前置交付，后续作为减小误判和省电的增强能力。首轮算法根据已有信号与时间运行，保留手动兜底并标记缺失数据；无心率信号和长时间静止不能自动等同入睡。

## 8. 软件组织与复用原则

沿用候选平台已有的 SDK、RTOS、显示与图形库版本形成基线，避免同步重写平台和产品。业务状态拥有明确更新入口，UI 保留合理的滚动/拖动/动画状态，服务处理异步工作与超时，板级适配实现硬件和电源控制。

先完成真实路径，再根据重复需要提取公共实现。不以层数、纯 C、单个大状态结构体或五个状态保证架构质量，不提前为未确定的双芯片建立复杂协议。

旧 `WatchCore`、状态快照、页面意图、F411 UI 与传感器代码逐项评估复用，核对 LVGL 版本、线程上下文、输入模型和资源限制。既不承诺逐行迁移，也不整体推倒重写。

PC 模拟器用于辅助逻辑和交互调试，业务行为及时在目标板验证。每周保留可运行结果和一项理解证据，例如能解释、预测或定位一条关键路径；AI 跑通不等于用户已掌握。

## 10. 追加投入与停止条件

追加预算必须对应物料、金额、要验证的问题、已有成果与失败后的停止条件。可以支撑追加的证据包括：AMOLED 交互通过需要集成附件、BLE 最小路径成立需要电池/振动、已找到主要耗电项需要验证硬件改进、睡眠数据链路成立需要存储/连接附件。

| 触发点 | 决策 |
|---|---|
| 无可核验 AMOLED 配套或完整报价不符合预算 | 不按该路线主采购，核验其他组合或提出明确预算差额 |
| SDK 关键能力受封闭边界阻断 | 记录必需能力与复现实例，重评平台；不能仅以代码开源比例判断 |
| 两周 UI 验证失败 | 找输入、渲染、传输或资源原因；先解决或换路线，不继续堆页 |
| Gadgetbridge 八小时无最小路径 | 取消默认，评估 Android 替代路径与成本，不自动扩大范围 |
| 必需负载耗尽七天预算 | 尽早评审主要耗电项；有明确改善再继续，无可行路径则暂停追加 |
| 传感器失败导致持续运行 | 先修超时和资源释放，不以假值或关闭异常日志绕过 |
| 睡眠阶段结束数据链路仍不稳定 | 停加传感器并修链路；算法不足与数据不足分别处理 |
| 长期只有模拟器、重构或外围例程进展 | 回到一项可测真机路径，限定下一项实验与时间 |
