## 关键依赖与容易漏掉的工作

源码 `apps/product/src/main.c:44–91` 的 `screen_off()` 停止 LVGL 定时器、关闭触摸和显示，然后无限等待 `key_events`；当前只有 KEY1 发送该事件。`apps/product/project/proj.conf:6–7` 关闭 PM/BLE。接通知、IMU 或闹钟之前，必须区分“后台事件到达”“是否允许提醒”“是否点亮屏幕”：勿扰可以抑制打扰，但不能靠不处理事件来实现。具体事件机制随最小路径设计，不提前重构全部框架。

建议下一阶段共同处理以下依赖：

- **通知生命周期**：收到、更新、去重、手机撤回、本地删除和断连后重连不是同一个动作；只有协议实验能确定手机侧能力。配对/解绑、通知访问权限、Android 后台限制也属于真实链路验收。
- **提醒规则**：沿用本轮已确认的通知预览、亮屏浮窗、通知中心和勿扰契约，自动展示不能成为离开草稿或秒表的操作；主动打开消息按既有退出确认处理。持续亮屏、翻腕和闹钟等关联状态进入增量回归，不重新访谈已确认交互。
- **计时与日期**：倒计时宜依据经过时间，闹钟和每日步数依赖可信日期；手机校时、跨天、重启与无效时间会影响结果。RTC 丢时不能用 Flash 旧时间掩盖；完整计步应另列跨天与保存验收。
- **低功耗条件**：事件唤醒、采样启停、超时和资源释放应随功能接入；整机电流、动态能量和电池续航分开测。关屏时的共享电源动作会影响传感器、音频和充电路径，见 [硬件记录](HARDWARE.md)。
- **可靠性与版本**：每个增量留固件标识、事件原因及复现步骤；已有 30–60 分钟联合验收线在阶段集成时执行，不能用单项点击通过代替。保存中断与重连压力测试应对应实际故障路径，不先搭庞大诊断平台。

## 推进顺序

用户本轮确认：先手机通知闭环；BLE 最小链路后尽早验证 PM；完整硬件清单并行准备、分批买；传感器先做 IMU/翻腕与基础计步实验。A 完成后即进入 P，不等所有通知外观完成才接 PM；P 与 B 在同一产品目标逐步集成。硬件选型准备与软件主线同时推进，实际接入按兼容性证据和到货情况安排，不机械等到 E 才用电机或电池。

|---|---|---|
| A. 手机最小链路 | 现有 Android 手机真实连接、断开/重连、校时、一条通知及删除；记录失败属于固件、协议、权限还是后台限制 | 沿用 Gadgetbridge 累计最多 8h；开始先核对已有用时，不自动重新计时。不先做全部通知 UI |

## 手机协议的首轮事实

2026-09-26 只读核对公开资料，远程源码来自当时 `master`，未锁定 APK/远程源码版本，须在实际实验开始时记录版本：

- [Gadgetbridge 的 Bangle.js 支持](https://gadgetbridge.org/gadgets/wearables/banglejs/) 明确支持具备 Nordic UART 服务并解码 JSON 的其他设备，不要求手表运行 Espruino；这是实验依据，不是本项目兼容证明。
- [协议文档](https://gadgetbridge.org/internals/specifics/banglejs-protocol/) 使用手机到设备 `GB({...})\n`、设备到手机换行分隔 JSON；[Espruino 说明](https://www.espruino.com/Gadgetbridge) 另含前导控制字符。NUS service/手机写入/手机订阅特征分别为 `6e400001`/`6e400002`/`6e400003` 加 `-b5a3-f393-e0a9-e50e24dcca9e`。实际传输会按 MTU 分片，不能按一次 GATT 写入解析一整条。
- 当前 [BangleJSDeviceSupport.java](https://codeberg.org/Freeyourgadget/Gadgetbridge/src/branch/master/app/src/main/java/nodomain/freeyourgadget/gadgetbridge/service/devices/banglejs/BangleJSDeviceSupport.java) 的 `transmitTime()` 发送 `setTime(...);E.setTimeZone(...)` 等命令，不能只实现通知 JSON 后宣称支持手机校时。只识别需要的命令子集，不执行手机传入的任意脚本。
- 文档支持 `notify`、`notify~`、`notify-`；当前 `onNotification()` 可能以同 id 的 `notify` 更新，所以必须按消息身份验证更新/去重。`onDeleteNotification()` 发送 `notify-`；设备发 `{"t":"notify","id":...,"n":"DISMISS"}` 是额外的手机清除请求，不等于只删本地记录。真实 APK 和不可清除通知行为待测。
- 中文存在适配风险：`renderUnicodeAsImage()`、Text as Bitmaps 与 ISO-8859-1 输出使传输未必是普通 UTF-8 正文。首轮必须观察真实中文和长消息的实际帧，验证可显示的文字路径；不只用英文 Debug 通知判断成功。
- [BangleJSCoordinator.java](https://codeberg.org/Freeyourgadget/Gadgetbridge/src/branch/master/app/src/main/java/nodomain/freeyourgadget/gadgetbridge/devices/banglejs/BangleJSCoordinator.java) 同时有 NUS 扫描过滤与名称匹配规则，bonding 为询问式。发现、配对/加密、通知订阅、通知访问权限和 iQOO 后台限制均纳入实验，不承诺任意广播名即被识别。
- 官方文档未给出离线通知补送保证；活动数据补取不是通知补送。原有离线补送后置决定保留。
- 固定 SDK `example/ble/peripheral/src/main.c` 已有 128-bit 自定义 GATT、写入/CCCD 回调、`sibles_register_svc_128()` 和 `sibles_write_value()` 入口，证明可研究复用，不是现成 NUS 或 Gadgetbridge 产品服务。

首个实验沿用累计 8h 上限，分别记录平台准备与协议调试耗时。成功应包含真实手机消息、可解释的中文路径、同 id 更新、手机撤回、已选本地删除行为及主动断开/重连；超时形成具体阻断和最小 Android 替代成本评估，不自动延长，也不自动启动完整手机 App 项目。协议成立之后再完整细化通知 UI。

## 已确认的通知行为

Q5、Q6、Q9–Q11 的最终规则如下；它们覆盖先前“息屏也使用顶部浮窗”的讨论建议。完整交互契约同步到 [通知中心与提醒](UI-INTERACTION.md#32-通知中心与新消息提醒)。

| 场景 | 展示与入口 | 保留与退出 |
|---|---|---|
| 正常亮屏收到消息 | 顶部小浮窗显示简略内容，沿用既有 3 秒自动收起；点击进入表盘下拉的消息页面，再查看详情 | 自动到达不强制离开当前页面 |
| 息屏收到消息且非勿扰 | 点亮独立通知预览页；无操作 5 秒后重新息屏；点击进入通知中心内该条消息的详情 | 预览展示和超时不丢组件草稿、不停止前台秒表；原长睡回表盘规则继续适用 |
| 主动点击浮窗或预览，当前有未提交新页/秒表数据 | 先走原有放弃草稿或停止清零确认，确认后到消息目标；息屏预览目标为该条详情 | 取消留在原操作页面，消息仍在通知中心；预览到期不是一次用户确认 |
| 勿扰开启 | 有 BLE 连接时继续收消息，不亮屏、不振动、不显示浮窗或预览 | 闹钟/倒计时到期仍提醒；翻腕开关独立，勿扰不等于断连或睡眠模式 |
| 手表删除单条或清空 | 只移除手表本地记录，不发送手机清除请求 | 手机通知保留；双向删除留待后续明确功能 |
| 手机主动撤回 | 按消息身份移除手表对应记录 | 是否覆盖所有应用/不可清除通知由实际协议实验记录 |

通知中心继续沿用倒序、最多 10 条的既有范围，详情支持多行；离线补送没有承诺。临时预览与用户主动导航分开处理，返回/KEY1 及既有页面恢复逻辑不因新增提醒另起一套规则。变暗态首次输入过滤仍适用。

## 首个实验：Product 的手机最小链路

**问题**：锁定 SDK 与现有 iQOO Android 手机，能否通过 Gadgetbridge 跑通真实通知和中文内容，并在 Product 息屏时继续处理连接与通知事件？

**预算**：沿用 Gadgetbridge 累计最多 8h，包括平台前置准备和协议调试，分别记账。本次已做公开协议预查，实施前把这部分研究及历史尝试计入用时记录，不能把预算重新归零。以下技术步骤不增加新的产品需求。

1. 固定并记录手机系统、Gadgetbridge APK/源码版本、通知权限及后台条件；在固定 SDK 自定义 GATT 示例上核对发现、连接、订阅和配对要求，形成最小服务入口。
2. 接入有长度上限的分片重组、通知身份/内容和最小校时命令；验证截断、超长、未知或畸形输入不会破坏已有状态，确保 SDK 回调不直接操作 LVGL。
3. 放入现有 Product 服务路径，以最小可读视图或诊断记录展示真实消息；拓展息屏事件处理，区分消息已接收与是否允许点亮屏幕。此步的普通息屏测试不宣称深睡通过。

5. 若路径成立，尽早进入 P 的同一固件 PM/事件唤醒实验，并按上表完成通知交互；若累计 8h 到期仍有阻断，交付明确复现和替代方案成本，停止无界扩展 Gadgetbridge。
